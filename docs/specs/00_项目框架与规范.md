# 00 项目框架与规范

## 文档目的
本文件是 RAG 企业知识库项目的共享规范基线。所有线程涉及接口、字段、日志、错误码、环境变量和协作方式的变更，必须先与本文件对齐，再进入实现。

## 工程目录蓝图
推荐目录如下：

```text

  supabase/
  environments/
  monitoring/

evaluation/

```

目录职责约束：
- `docs/specs`：跨线程共享规范，必须先更新文档再视为生效。
- `docs/tasks`：模块任务清单，描述目标、边界、交付物和验收。
- `docs/changes`：模块实施记录，描述本轮实现、变更、风险与下一步。
- `frontend`：仅承载前端页面、组件、类型与数据访问逻辑。
- `backend`：仅承载后端 API、领域服务、数据模型、任务处理与测试。
- `infra`：部署、环境、平台配置和自动化脚本。
- `evaluation`：评测数据、报告模板和回归结果。

禁止跨层依赖：
- 前端不得直接依赖后端内部实现。
- `schemas` 不得依赖 `services`。
- `repositories` 不得调用 API 层。
- 业务模块不得自行定义与共享规范冲突的字段命名。

## 命名与分层规范
命名规则：
- 目录和资源路径使用 `kebab-case`。
- Python 文件、模块、变量使用 `snake_case`。
- TypeScript 组件、类型使用 `PascalCase`，普通变量使用 `camelCase`。
- API 资源使用名词复数，如 `/knowledge-bases`、`/documents`。

后端分层：
- `api`：路由和请求入口。
- `schemas`：请求/响应 DTO 与结构化数据定义。
- `services`：业务流程编排。
- `repositories`：数据访问。
- `workers`：异步任务处理。
- `core`：配置、日志、鉴权、错误码等基础能力。

前端分层：
- `app`：路由与页面。
- `features`：按业务域组织的页面逻辑。
- `components`：可复用 UI 组件。
- `lib`：请求封装、工具函数、配置。
- `types`：共享类型定义。

## API 契约模板
版本策略：
- `v1` 仅允许兼容性新增。
- 破坏性变更必须进入 `/api/v2`。

命名规则：
- 前缀统一为 `/api/v1`。
- 资源路径使用名词复数加 `kebab-case`。
- 示例：`/api/v1/knowledge-bases/{kb_id}/documents/{doc_id}`。

统一响应结构：

```json
{
  "code": "OK",
  "message": "success",
  "data": {},
  "request_id": "req_123",
  "trace_id": "trace_123",
  "ts": "2026-03-28T12:00:00Z"
}
```

统一错误结构：

```json
{
  "code": "DOC_NOT_FOUND",
  "message": "document not found",
  "details": {},
  "request_id": "req_123",
  "trace_id": "trace_123"
}
```

分页、过滤、排序约定：
- 分页参数统一使用 `page`, `page_size`。
- 过滤参数按业务字段直接透出，如 `status`, `format`, `kb_id`。
- 排序参数统一使用 `sort_by`, `sort_order`。

## 错误码规范
错误码采用字符串域前缀风格，示例如下：

- `COMMON_INVALID_ARGUMENT`
- `COMMON_NOT_FOUND`
- `COMMON_CONFLICT`
- `COMMON_RATE_LIMITED`
- `COMMON_INTERNAL_ERROR`
- `AUTH_UNAUTHORIZED`
- `AUTH_FORBIDDEN`
- `DOC_NOT_FOUND`
- `DOC_PARSE_FAILED`
- `CHUNK_BUILD_FAILED`
- `RETR_TIMEOUT`
- `QA_CONTEXT_EMPTY`

建议 HTTP 状态码映射：
- 参数错误：`400`
- 未认证：`401`
- 无权限：`403`
- 资源不存在：`404`
- 冲突：`409`
- 限流：`429`
- 内部错误：`500`

## 日志与追踪规范
链路规则：
- `request_id`、`trace_id` 由网关统一注入。
- 服务端负责透传、补齐上下文字段并写入日志。

通用必填字段：
- `timestamp`
- `level`
- `service`
- `env`
- `request_id`
- `trace_id`
- `span_id`
- `user_id`
- `kb_id`
- `doc_id`

请求日志字段：
- `method`
- `path`
- `status_code`
- `latency_ms`
- `client_ip`
- `user_agent`

任务日志字段：
- `task_id`
- `task_type`
- `stage`
- `retry_count`
- `duration_ms`
- `result`

异常日志字段：
- `error_code`
- `error_type`
- `stack`
- `safe_message`

脱敏要求：
- 日志中禁止记录真实密钥、原始凭证和完整敏感文本。
- 错误详情对外输出必须使用脱敏后的 `safe_message`。

## 环境变量规范
命名规则：
- 全大写下划线风格。
- 采用域前缀：`APP_*`, `DB_*`, `SUPABASE_*`, `LLM_*`, `EMBEDDING_*`, `LOG_*`, `AUTH_*`。

分层规则：
- 使用一份主清单统一维护。
- 环境按 `.env`, `.env.test`, `.env.prod` 分层。
- 禁止提交真实密钥。

最小必填集合：
- `APP_ENV`
- `APP_PORT`
- `DB_URL`
- `SUPABASE_URL`
- `SUPABASE_KEY`
- `LLM_API_KEY`
- `EMBEDDING_MODEL`
- `LOG_LEVEL`

## 模块边界与协作规则
职责边界：
- `00` 模块只产出规范，不实现业务功能。
- `01` 负责文档解析与结构化。
- `02` 负责语义分块。
- `03` 负责向量化与向量存储。
- `04` 负责混合检索与重排。
- `05` 负责答案生成与溯源。
- `06` 负责前端交互与管理后台。
- `07` 负责评测体系与验收执行。
- `08` 负责部署与运维。

协作规则：
- 任何影响其他线程的改动，必须先更新 `docs/specs` 或对应 `docs/changes`。
- 主线程只认仓库文档，不认纯对话结论。
- 子线程发现规范冲突时，只能提待确认项，不得自行改动共享契约。

## 实施与发布规则
- 共享规范由主线程审批后视为 `spec-v1` 基线。
- 业务模块编码时，必须同步维护模块实施记录。
- 未写入文档的改动，不视为对外生效。

## 验收标准
- 新线程根据文档在 30 分钟内完成入场准备的通过率不低于 90%。
- 所有 API 文档使用统一响应模板，覆盖率 100%。
- 所有错误响应包含 `code`, `message`, `request_id`, `trace_id`，覆盖率 100%。
- PRD 关键字段命名一致性 100%。
- `00` 模块不包含业务实现，边界审查通过率 100%。
